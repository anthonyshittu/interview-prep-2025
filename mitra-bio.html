Likely Interview Questions

Q How would you decide whether to use a Server Component or Client Component for a given piece of UI? ▶
Start Server Component by default. Shift to Client only when I need: interactivity (event handlers, hooks), browser APIs, or real-time subscriptions. The decision tree I use:
  • Does it fetch data? → Server (async component)
  • Does it respond to user interaction? → Client
  • Does it use useState, useEffect, useContext? → Client
  • Is it a layout wrapper or pure display? → Server
Key point: I push Client Components as deep in the tree as possible so the bundle is minimal. For example, a product page is a Server Component, but the "Add to Cart" button is a small Client Component imported into it.
Q How do you handle authentication with Next.js App Router? ▶
I've used NextAuth.js (Auth.js v5) and custom JWT solutions. In App Router:
  • Use Middleware (middleware.ts) to protect routes before they render — redirect unauthenticated users at the edge
  • Read session in Server Components via getServerSession() or the new auth() helper
  • Pass auth token from server to Client Components via props, not exposed to window
  • For Mitra Bio's use case: skin reports are private data — hard protection at middleware level, secondary check at API route level
Never trust client-side auth checks alone. Always validate on the server.
Q Walk me through how you'd build a "skin results dashboard" page from a performance perspective. ▶
Architecture approach:
  • Route: /app/results/[reportId] — dynamic, user-specific, no SSG (personal data)
  • Auth wall: Middleware verifies JWT, redirects if unauthenticated
  • Layout: Server Component fetches user metadata (name, kit status) — fast, no JS cost
  • Streaming: Wrap heavy sections (charts, ML insights) in Suspense with skeleton loaders — user sees header instantly
  • Data: Multiple parallel fetches for different report sections, streamed independently
  • Charts: Client Component using a library like Recharts or Nivo, lazy-loaded with dynamic(() => import(...))
  • Prefetch: Prefetch report data during "processing" screen so results appear instantly when navigated to

Common Interview Questions

Q What's the difference between interface and type in TypeScript? When do you use each? ▶
Both define shapes. Key differences:
  • interface: Declaration merging (can be extended across files), class implementation, slightly better error messages for object shapes
  • type: Can represent unions, intersections, primitives, tuples, mapped types — more expressive
  • My rule: Use interface for public API shapes and class contracts. Use type for unions, computed/mapped types, and aliases for complex types.
  • In practice at a company like Mitra Bio: I'd use interface for domain models (SkinReport, User, Product) and type for state unions, utility types, and function signatures.
Q How do you handle strict null checks and avoid null-related runtime errors? ▶
Always enable "strict": true in tsconfig which enables strictNullChecks. Practices I follow:
  • Use optional chaining (report?.biomarkers?.[0]?.score) for safe access
  • Nullish coalescing (score ?? 0) instead of || (which also catches 0, '')
  • Explicit guard functions: if (!report) return <EmptyState /> before use
  • Never use non-null assertion (!) unless I have a 100% guarantee — use type guards instead
  • Zod validation at API boundaries so data entering my types is guaranteed non-null where declared

// app/api/webhooks/shopify/route.ts
import { createHmac } from 'crypto'

export async function POST(req: Request) {
  const body = await req.text()
  const hmac = req.headers.get('x-shopify-hmac-sha256')

  // Always verify webhook signatures
  const digest = createHmac('sha256', process.env.SHOPIFY_WEBHOOK_SECRET!)
    .update(body, 'utf8').digest('base64')

  if (digest !== hmac) return new Response('Unauthorized', { status: 401 })

  const event = JSON.parse(body)

  switch (req.headers.get('x-shopify-topic')) {
    case 'orders/paid':
      await triggerSampleKitDispatch(event)
      break
    case 'orders/fulfilled':
      await notifyCustomerOfDelivery(event)
      break
  }

  return new Response('OK', { status: 200 })
}

BFF & API Architecture
Backend-for-Frontend is explicitly mentioned in the JD. Know why it exists, when to use it, and how to build it with Next.js.

What is a BFF?

A Backend-for-Frontend is a dedicated API layer that sits between your frontend and your downstream services. Rather than the frontend calling multiple services directly, the BFF aggregates, transforms, and adapts data specifically for the frontend's needs.

Without BFF
  • Frontend calls Shopify, reports API, user API separately
  • Waterfall fetches — slow
  • Frontend receives more data than needed
  • Auth logic duplicated or exposed
  • Multiple API tokens in client bundle
With BFF
  • One call to BFF → BFF fans out to services in parallel
  • Aggregated, shaped response tailored to UI needs
  • Secrets/tokens stay on server
  • Auth enforced at BFF layer
  • Easy to iterate without touching downstream services

BFF with Next.js Route Handlers

// app/api/dashboard/route.ts — BFF endpoint for user dashboard
export async function GET(request: Request) {
  const session = await getServerSession()
  if (!session) return Response.json({ error: 'Unauthorized' }, { status: 401 })

  // Fan out to multiple services in parallel
  const [latestReport, orderHistory, recommendations, subscription] = await Promise.allSettled([
    fetchLatestReport(session.user.id),       // Data Science API
    fetchOrderHistory(session.shopifyCustomerId), // Shopify Admin API
    fetchRecommendations(session.user.id),     // ML Recommendations
    fetchSubscriptionStatus(session.user.id),  // Billing Service
  ])

  // Shape response for the frontend — only what's needed
  return Response.json({
    report: latestReport.status === 'fulfilled' ? latestReport.value : null,
    orders: orderHistory.status === 'fulfilled' ? orderHistory.value.map(toOrderSummary) : [],
    recommendations: recommendations.status === 'fulfilled' ? recommendations.value : [],
    isPremium: subscription.status === 'fulfilled' ? subscription.value.active : false,
  })
}
Note: Promise.allSettled vs Promise.all Use allSettled so one failing service doesn't crash the whole dashboard. The frontend handles partial data gracefully — show what you have, indicate what failed.

Interview Questions

Q When would you not use a BFF? What are its drawbacks? ▶
BFFs add complexity — another layer to maintain, another failure point, another performance hop. I'd avoid them when:
  • The app only calls one or two simple APIs — not worth the overhead
  • Services are already well-aggregated (e.g., a GraphQL API already returns what you need)
  • Team is very small — the BFF just means more code to own
For Mitra Bio, a BFF makes sense because: multiple distinct services (Shopify, data science platform, billing), sensitive API keys that must not be exposed, and complex data aggregation for the dashboard. The trade-off is worth it.
Q How do you handle error propagation from backend services through a BFF to the UI? ▶
I use a layered approach:
  • At the service call: Wrap in try/catch, convert to a typed error result — never let raw service errors propagate
  • At the BFF: Use Promise.allSettled — partial data is better than no data. Log errors with correlation IDs for debugging.
  • HTTP status codes: Return meaningful status (401 for auth, 404 for not found, 503 if critical service is down)
  • Error shapes: Return consistent { error: { code, message, retryable } } that the frontend can pattern-match on
  • In the UI: Discriminated union states — idle / loading / success / error. Show recovery options (retry, contact support) based on error type.

Core Web Vitals — What They Are & Why They Matter

LCP

Largest Contentful Paint

Time until the largest visible element renders. Target: < 2.5s. For Mitra Bio: the hero image or product photo.

Fix: Preload hero image, use Next.js Image with priority, server-side render critical content.

CLS

Cumulative Layout Shift

Unexpected layout movement. Target: < 0.1. A price jumping around on load feels broken and untrustworthy.

Fix: Set image dimensions, use skeleton loaders with fixed dimensions, avoid injecting content above existing.

INP

Interaction to Next Paint

Responsiveness to user input. Target: < 200ms. Replaced FID in 2024. Measures all interactions.

Fix: Avoid long tasks on main thread, use startTransition for non-urgent updates, debounce search inputs.

System Design Interview Questions

Q How would you design the status tracking system between sample collection and results delivery? ▶
I'd model this as an explicit state machine — a finite set of states with valid transitions between them.
  • States: kit_ordered → kit_dispatched → kit_in_transit → sample_received → processing → analysis_complete → results_ready → error
  • Storage: A report_events table (append-only log of state transitions) + a reports table with the current state denormalised for fast reads
  • Transitions triggered by: Shopify webhooks (kit_dispatched), carrier API webhooks (in_transit), Lab LIMS callback (sample_received, processing, complete)
  • Frontend polling: SSE endpoint polls report status every 5s; switches to push when status is results_ready
  • Notifications: Each state transition emits an event to a queue; notification service consumes and sends email/push as configured
  • Idempotency: All webhook handlers are idempotent — duplicate deliveries don't cause double state transitions
Q How would you handle a scenario where Shopify's API is down — how does this affect the customer experience? ▶
Defence in depth — the UI should never be completely broken because one upstream service is down.
  • Product pages: ISR means Shopify outage doesn't affect the storefront — pages are pre-built and served from CDN
  • Cart: Show a graceful error on cart mutations. Never lose cart state — cartId in cookie survives the outage
  • Checkout: Shopify hosts checkout — if they're down, checkout is down. Honest error message + email capture for "notify me when back"
  • Dashboard: Use Promise.allSettled in BFF — Shopify order history fails silently, rest of dashboard still loads
  • Circuit breaker: Wrap Shopify calls in a circuit breaker — after 5 consecutive failures, skip the call and return cached data for 60s before retrying
  • Monitoring: Alert on Shopify API error rate spike so you know before customers do
Q The data science team wants to A/B test two different recommendation algorithms. How do you support this in the frontend? ▶
  • Experiment assignment: Assign user to variant server-side (BFF or middleware) using a deterministic hash of userId + experiment ID — stable across sessions
  • Variant in BFF response: Return variant: 'control' | 'treatment' alongside recommendations so the frontend can render differently if needed
  • Logging: Every recommendation impression and click-through logged with the variant — send to analytics pipeline (Segment, Amplitude, or custom)
  • Feature flags: Use a feature flag system (LaunchDarkly, PostHog, or custom) to control experiment rollout %, enable/disable without deploy
  • Separation: The recommendation API abstraction means the frontend doesn't know or care which algorithm is running — just receives product IDs
  • Clean-up: Once winner is determined, remove the experiment code in a single PR — no flag debt

// app/api/report/[id]/stream/route.ts
export async function GET(req: Request, { params }: { params: { id: string } }) {
  const session = await getSession(req)
  if (!session) return new Response('Unauthorized', { status: 401 })

  let interval: ReturnType<typeof setInterval>

  const stream = new ReadableStream({
    async start(controller) {
      const send = (data: unknown) =>
        controller.enqueue(new TextEncoder().encode(`data: ${JSON.stringify(data)}\n\n`))

      interval = setInterval(async () => {
        const report = await db.getReport(params.id)

        // Guard — only owner can stream their report
        if (report.userId !== session.userId) { controller.close(); return }

        send({ status: report.status, updatedAt: report.updatedAt })

        if (report.status === 'ready' || report.status === 'error') {
          clearInterval(interval)
          controller.close()
        }
      }, 4000)
    },
    cancel() { clearInterval(interval) }  // cleanup on client disconnect
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
    }
  })
}

Real-time Interview Questions

Q Why would you choose SSE over WebSockets for the report status feature? ▶
  • Directionality: Status updates are server → client only. WebSockets are bi-directional — that bi-directionality adds complexity with no benefit here.
  • Infrastructure: SSE works over standard HTTP/2. WebSockets need a persistent TCP connection and specific infrastructure support. Vercel Edge Functions don't support WebSockets natively.
  • Reconnection: SSE reconnects automatically after disconnect — built into the browser spec. WebSockets need custom reconnection logic.
  • Simplicity: SSE is just an HTTP endpoint with a special content-type. Easier to test, debug, and monitor.
  • When I'd use WebSockets instead: If we built a collaborative feature (e.g., two users reviewing a report together in real-time), bi-directionality would justify the complexity.
Q The SSE connection keeps getting dropped on mobile. How do you handle this? ▶
  • SSE auto-reconnect: The browser's EventSource API reconnects automatically after drop — it sends a Last-Event-ID header so you can resume from where you left off
  • Server-side IDs: Send an id: field with each event so the client can recover on reconnect
  • Keep-alive: Send a comment line every 30s (: keepalive\n\n) to prevent intermediary proxies from closing the connection
  • Background/tab invisible: When user switches apps on mobile, the connection may freeze. On visibilitychange event, close and reopen the SSE connection
  • Graceful fallback: If SSE fails 3 times, fall back to polling every 10s — worse UX but reliable
  • Push notification backup: The real safety net — even if the SSE drops, the push notification fires when results are ready

Database Interview Questions

Q Would you store biomarkers as one column (JSON) or as separate rows? Trade-offs? ▶
I'd use separate rows (EAV pattern — Entity-Attribute-Value) for biomarkers, not JSON. Here's why:
  • Queryability: With rows I can run WHERE key = 'hydration' AND score > 80 efficiently. With JSON, that requires a JSON path expression and can't use a standard B-tree index.
  • Indexing: I can index on (key, score) for population stats. JSON columns need GIN indexes which are larger and slower.
  • Schema evolution: Adding a new biomarker type is just inserting new rows — no schema migration needed.
  • Aggregations: SQL window functions for trend analysis work cleanly on rows
  • When JSON is fine: For the insights field (natural language text, no querying needed) — JSONB column is perfectly appropriate.
Q How do you handle database migrations safely in production with no downtime? ▶
  • Expand/contract pattern: Never do a breaking change in one migration. Phase 1: add new column (nullable). Phase 2: deploy code that writes to both. Phase 3: backfill old rows. Phase 4: add NOT NULL constraint. Phase 5: remove old column.
  • Never rename a column in one step — add new column, migrate data, remove old one over multiple deploys
  • Avoid locking migrations: ADD COLUMN NOT NULL DEFAULT on large tables locks the table. Use ADD COLUMN DEFAULT NULL then set default separately.
  • Test on production data size: Migrations that take 2ms on dev can take 4 minutes on 10M rows
  • Tools: Prisma Migrate with --create-only to review before applying; Atlas for more complex migrations
  • Rollback plan: Every migration should have a down migration. Test it before deploying up.

Performance & Architecture

What is a circuit breaker pattern and why would you use it with Shopify's API?
A circuit breaker monitors calls to an external service. After N failures in a window, it "opens" — subsequent calls fail fast (without trying) for a timeout period, then "half-open" to test if the service recovered.

Why with Shopify: if Shopify is slow/down, without a circuit breaker every user request waits for Shopify's timeout (30s) — server exhausted. With breaker, calls fail in ms and return cached data or a graceful error.

Explain the difference between Promise.all and Promise.allSettled — when do you use each in a BFF?
Promise.all: Fails fast — if any promise rejects, the whole call rejects. Use when all data is required (e.g., you can't render the page without any of it).

Promise.allSettled: Waits for all promises, collects results and rejections. Use in a BFF dashboard where partial data is better than no data — Shopify order history failing shouldn't break the whole dashboard.

N+1: Fetching a list of N items, then making a separate DB query for each — 1 query + N queries = terrible performance.

  reference_range_min: number;

  id: string;
  value: number;
  range: { min: number; max: number };
  methylationScore: number;
  collectedAt: Date;

};

  const { reference_range_min: min, reference_range_max: max, measured_value: value } = raw;

    id: raw.biomarker_id,
    value,
    range: { min, max },
    methylationScore: raw.methylation_score,
    collectedAt: new Date(raw.collected_at),
    status: value < min ? 'low' : value > max ? 'high' : 'optimal',
  };
}

Q&A

QHow do you decide what data transformation to do in the BFF vs the frontend component?▶

The BFF should handle anything that: (1) touches raw upstream schemas that might change, (2) requires secrets or server-only context, (3) needs to be cached at the server layer, or (4) aggregates multiple services. The frontend component should only handle presentation logic — formatting a date for display, picking a colour based on status, deciding which variant of a component to render. If a transformation runs in multiple components, it belongs in the BFF or a shared utility. The goal is components that receive data already shaped for their needs — no raw.data[0].biomarker_results.v2.score in JSX.

QThe data team changes an upstream API field name. How do you handle it with minimal blast radius?▶

This is why the BFF normalisation layer exists. The change only needs to be made in one place — the transformation function at the BFF boundary. The frontend never saw the raw field name. Use a Zod schema to parse the upstream response: z.object({ methylation_score: z.number() }) — the parse will throw immediately if the field is missing or renamed, giving you a clear error in logs rather than a silent NaN in the UI. Add the new field name to the Zod schema, update the mapping function, deploy. No frontend changes needed.

QWhich charting library would you choose for epigenetic biomarker dashboards and why?▶

For most of the dashboard — trend lines, bar charts, range indicators — Recharts: it's React-first, declarative, composable, and handles responsive containers well. For anything requiring custom layout algorithms or complex statistical visualisations (heatmaps, scatter plots with brush selection, parallel coordinates for multi-biomarker views) — D3 for math/layout only, React for DOM. This avoids the D3 vs React DOM ownership fight. Never let D3 call selection.append() inside a React component — use D3's scales and paths, then write the JSX yourself. For a skincare/wellness product, I'd also prioritise aesthetics and animation quality — Recharts with custom SVG shapes and Framer Motion for transitions can look premium without heavy custom code.

          unsubscribe();
        }
      });

    },
  });

}

Speaking the Data Team's Language

When they say "pipeline"

They mean a sequence of data processing steps — raw kit → quality check → feature extraction → model scoring → result. Know where your API call sits in this pipeline so you can set correct user expectations (e.g., "results available 48 hours after kit receipt").

When they say "schema"

They mean the data structure contract. Show you think about schemas too — "I'd represent that as a Zod schema on the frontend side so any drift is caught at runtime rather than silently breaking the UI."

When they say "model output"

They mean the result of an ML/statistical model — a score, a classification, a probability. Ask: "Is this deterministic for the same input, or can it change as the model is retrained?" — this determines your caching strategy.

When they say "feature"

In data science this means an input variable to a model (e.g. age, diet score, methylation level) — not a product feature. Knowing this distinction signals you've worked with data scientists before.

Data Privacy in Personalisation

Never Expose Raw Scores

A methylation score of 0.23 on ELOVL2 is meaningless and potentially alarming to a user. Always translate to qualitative language ("Your skin's moisture retention is lower than optimal") — and only show what the user consented to see.

Genetic Data = Special Category

Under GDPR Article 9, genetic data is special category data. It requires explicit consent (not just soft opt-in), a lawful basis (typically explicit consent or vital interests), and a DPA / privacy notice that specifically covers it.

Data Minimisation in the BFF

The BFF should strip any field the UI doesn't need before sending to the client. If the recommendation API returns raw feature values, strip them — the browser never needs to see them. Less data in the client = smaller attack surface.

Right to Erasure

A user can request deletion of their genetic data. This must cascade: Shopify customer record, biomarker DB, recommendation model inputs, any cached results. As the frontend engineer you own the UI for this flow — and you need to know the full data map to build it correctly.

QHow do you connect the data team's recommendation scores to what a user actually sees on the page?▶

The BFF is the join layer. The data team exposes an API that returns ranked product handles with reason codes. The BFF calls that API in parallel with the Shopify Storefront API, joins on product handle, strips any raw score values, maps reason codes to user-facing copy ("Based on your ELOVL2 results, your skin needs extra moisture support"), and returns a clean product list to the frontend. The frontend component knows nothing about methylation scores — it receives products with a personalisation.reasonLabel field and renders it. This separation means the data team can retrain their model and change scores without touching any UI code.

QHow would you A/B test two different personalisation algorithms without the data team deploying new code each time?▶

The recommendation API should accept an optional modelVersion or experimentId parameter. The BFF reads a feature flag (LaunchDarkly / Statsig) that maps the current user to an experiment bucket and forwards the appropriate parameter to the data API. Neither the frontend nor the data pipeline changes when you run a new experiment — only the flag configuration does. Metrics (click-through on personalised products, conversion) are tracked via analytics events attached to products that carry their experiment bucket as a property. The data team analyses the results in their own tools. This keeps concerns cleanly separated.

QHow does GDPR specifically affect how you build the personalisation data flow?▶

Lawful basis: genetic data requires explicit consent (Article 9) — the consent UI must be unambiguous, granular (separate consent for processing vs marketing), and revocable. Data minimisation: the BFF must not send raw genetic scores to the client — only derived, human-readable outputs. Storage limitation: results must not be cached indefinitely — the BFF cache TTL must respect data retention policies. Right to erasure: a deletion request must cascade through Shopify, the biomarker database, any BFF caches, and a signal to the data team to remove the user from model training data. Data portability: users can request a copy of their data — the export endpoint must be built and tested. These aren't afterthoughts — they shape the API contract design from day one.
