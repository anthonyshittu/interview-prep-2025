useRef for Real-Time Data

High-frequency WebSocket data should update a ref, not state. Committing to state at a capped frame rate prevents flooding React's reconciler.

'use client'
export function useLiveTelemetry(channel: string) {
  const buffer = useRef<TelemetryPoint[]>([])
  const [snapshot, setSnapshot] = useState<TelemetryPoint[]>([])

  useEffect(() => {
    const ws = new WebSocket(`/ws/telemetry/${channel}`)
    ws.onmessage = (e) => {
      buffer.current.push(JSON.parse(e.data))
    }
    // Commit to React state at 60fps max — not 200Hz
    const rafId = setInterval(() => {
      if (buffer.current.length) {
        setSnapshot(prev => [...prev, ...buffer.current.splice(0)])
      }
    }, 16)
    return () => { ws.close(); clearInterval(rafId) }
  }, [channel])

  return snapshot
}

Q&A

QHow do you prevent a React component from re-rendering on every WebSocket message?▶

Buffer incoming data in a useRef — refs don't trigger re-renders. Then use setInterval or requestAnimationFrame to commit the buffer to state at a capped rate (60fps / 16ms). This decouples the data arrival rate (could be 200Hz) from React's reconciliation cycle. Additionally: wrap the chart component in memo(), use useMemo for any expensive data transformation, and ensure the data you pass to the chart is stable in reference when content hasn't changed.

QWhy use branded/nominal types for engineering values like speed or time?▶

In an F1 data context, you might have a lap time in seconds, a sector delta in milliseconds, and a GPS timestamp in Unix milliseconds — all typed as number. Passing the wrong one to the wrong function compiles fine but produces incorrect analysis. Branded types add a nominal tag so TypeScript enforces that you can't accidentally pass a Milliseconds where a Seconds is expected. The overhead is zero at runtime — it's purely a compile-time guard. In safety-critical or precision-critical domains, this pattern catches a whole class of bugs that unit tests often miss.

Canvas vs SVG — The Core Trade-off

SVG

DOM-based, interactive

  • Each element is a DOM node — accessible, styleable, hoverable
  • Works well up to ~5,000 elements before performance degrades
  • Built-in CSS transitions and animations
  • Screen-reader accessible with ARIA attributes
  • Use for: sector indicators, lap comparison overlays, sparse aero data points, interactive selection handles
Canvas 2D / WebGL

Pixel-based, high performance

  • Draws pixels — no DOM nodes per data point
  • Handles 500,000+ points at 60fps
  • Manual hit-testing required for hover/click
  • Not inherently accessible — needs ARIA descriptions
  • Use for: full-lap telemetry traces, CFD pressure maps, high-frequency live data streams
The answer they want to hear "I'd use SVG for interactive UI elements and sparse overlays, Canvas for the actual data traces. A telemetry chart might render the 50,000-point speed trace on Canvas, then overlay SVG elements for DRS zones, sector markers, and the hover crosshair."

'use client'
import { useRef, useEffect } from 'react'

// Canvas-based telemetry renderer — handles 50k+ points at 60fps
export function SpeedTraceCanvas({ points, width, height, range }: Props) {
  const canvasRef = useRef<HTMLCanvasElement>(null)

  useEffect(() => {
    const canvas = canvasRef.current
    if (!canvas) return
    const ctx = canvas.getContext('2d')!

    // Device pixel ratio — crisp on retina displays
    const dpr = window.devicePixelRatio || 1
    canvas.width = width * dpr; canvas.height = height * dpr
    canvas.style.width = `${width}px`; canvas.style.height = `${height}px`
    ctx.scale(dpr, dpr)

    const xScale = (d: number) => ((d - range.xMin) / (range.xMax - range.xMin)) * width
    const yScale = (d: number) => height - ((d - range.yMin) / (range.yMax - range.yMin)) * height

    ctx.clearRect(0, 0, width, height)
    ctx.strokeStyle = '#e8002d'
    ctx.lineWidth = 1.5
    ctx.beginPath()

    points.forEach((p, i) => {
      const x = xScale(p.lapDistance), y = yScale(p.speed)
      i === 0 ? ctx.moveTo(x, y) : ctx.lineTo(x, y)
    })
    ctx.stroke()
  }, [points, width, height, range])

  return <canvas ref={canvasRef} aria-label="Speed trace" />
}

A 10-lap stint at 200Hz = 720,000 data points. Rendering all of them is unnecessary and slow. Downsample to the display resolution — typically 2–4 points per pixel.

// Largest Triangle Three Buckets (LTTB) — preserves visual shape while reducing points
// Industry-standard downsampling algorithm for time-series data
function lttbDownsample(data: TelemetryPoint[], targetCount: number): TelemetryPoint[] {
  if (data.length <= targetCount) return data
  const bucketSize = (data.length - 2) / (targetCount - 2)
  const sampled: TelemetryPoint[] = [data[0]]

  let a = 0
  for (let i = 0; i < targetCount - 2; i++) {
    const bucketStart = Math.floor((i + 1) * bucketSize) + 1
    const bucketEnd = Math.min(Math.floor((i + 2) * bucketSize) + 1, data.length)
    // Pick the point in this bucket that forms the largest triangle with the previous sampled point
    let maxArea = -1, maxIdx = bucketStart
    for (let j = bucketStart; j < bucketEnd; j++) {
      const area = Math.abs((data[a].lapDistance - data[j].lapDistance) * (sampled.at(-1)!.speed - data[j].speed))
      if (area > maxArea) { maxArea = area; maxIdx = j }
    }
    sampled.push(data[maxIdx]); a = maxIdx
  }
  sampled.push(data.at(-1)!)
  return sampled
}

Q&A

QHow would you render a 200Hz telemetry trace covering a full race stint without freezing the browser?▶
  • Canvas, not SVG — 200Hz × 5400s race = 1,080,000 points. SVG can't handle that. Canvas 2D renders them all in milliseconds.
  • LTTB downsampling — at a chart width of 1200px, you need at most ~2400 display points. Downsample to chart resolution using LTTB to preserve shape.
  • Off-screen canvas — render the trace to an off-screen canvas in a Web Worker, transfer the ImageBitmap to the main thread. Zero main-thread blocking.
  • Progressive loading — load first 10% of data, render, then load the rest in chunks. The engineer sees something immediately.
  • Zoom = re-downsample — when the user zooms into a 5-second window, re-downsample that range at full resolution from the raw data buffer.
QA Vehicle Performance engineer wants to compare three drivers' speed traces on the same chart. Walk me through your approach.▶
  • Align by lap distance, not elapsed time. Different lap times mean time-aligned traces are offset and misleading. Every channel is plotted against metres completed.
  • Shared scales — all three traces use the same Y-axis scale so visual comparison is accurate. Don't auto-scale per lap.
  • Delta trace — below the main chart, add a time-delta trace showing Driver B and C vs Driver A (the reference). This is the engineer's primary analysis tool.
  • Colour coding — each driver gets a distinct colour, persisted in URL state so the engineer can share the view with colleagues.
  • Channel switcher — same layout, switch between speed / throttle / brake / gear with a single click. State stays in sync.
  • Sector markers — vertical lines at sector 1 and 2 boundaries overlaid as SVG on top of the Canvas traces.

// Singleton WebSocket manager — one connection shared across all chart components
// Multiple components subscribing to the same channel don't create multiple connections

class TelemetryWSManager {
  private ws: WebSocket | null = null
  private subscribers = new Map<string, Set<(data: TelemetryPoint) => void>>()

  connect(url: string) {
    if (this.ws?.readyState === WebSocket.OPEN) return
    this.ws = new WebSocket(url)
    this.ws.onmessage = (e) => {
      const { channel, data } = JSON.parse(e.data)
      this.subscribers.get(channel)?.forEach(cb => cb(data))
    }
    this.ws.onclose = () => this.scheduleReconnect(url)
  }

  subscribe(channel: string, cb: (d: TelemetryPoint) => void) {
    if (!this.subscribers.has(channel)) this.subscribers.set(channel, new Set())
    this.subscribers.get(channel)!.add(cb)
    return () => this.subscribers.get(channel)!.delete(cb)
  }

  private scheduleReconnect(url: string, delay = 1000) {
    setTimeout(() => this.connect(url), delay)
  }
}

// Circular buffer to cap memory usage during long sessions
class CircularBuffer<T> {
  private buf: T[] = []
  constructor(private maxSize: number) {}
  push(item: T) {
    this.buf.push(item)
    if (this.buf.length > this.maxSize) this.buf.shift()
  }
  toArray() { return [...this.buf] }
}
// Exponential back-off reconnection with connection status tracking
// Engineers need to know if live data is stale — show connection state clearly

type ConnectionState = 'connecting' | 'live' | 'reconnecting' | 'offline'

function createReconnectingWS(url: string, onMessage: (e: MessageEvent) => void) {
  let ws: WebSocket, delay = 500, maxDelay = 15_000
  const [state, setState] = ['connecting' as ConnectionState]

  function connect() {
    ws = new WebSocket(url)
    ws.onopen = () => { delay = 500; /* setState('live') */ }
    ws.onmessage = onMessage
    ws.onclose = () => {
      // setState('reconnecting')
      setTimeout(() => { delay = Math.min(delay * 2, maxDelay); connect() }, delay)
    }
  }
  connect()
  return { close: () => ws.close() }
}

// Always show connection state in the UI — never silently show stale data

  const colors = { live: '#4ade80', reconnecting: '#fbbf24', offline: '#f87171', connecting: '#888' }
  return <span style={{ color: colors[state] }}>● {state.toUpperCase()}</span>
}

Q&A

QThe WebSocket drops during qualifying. What happens in the UI and how do you recover?▶
  • Immediate visual indicator — the connection state badge switches to "RECONNECTING" in amber. Engineers must never be looking at stale data without knowing it.
  • Exponential back-off reconnect — attempt at 500ms, 1s, 2s, 4s... cap at 15s. Don't hammer the server during a network blip.
  • On reconnect, request a gap fill — send the last received timestamp so the server can replay any missed points. This ensures the post-session analysis has a complete dataset even if the UI briefly disconnected.
  • Buffer the most recent N seconds — in a circular buffer. If reconnect is near-instant, the live trace is seamless. If it takes longer, the engineer sees a gap in the trace rather than corrupt data.
  • Never silently resume — when reconnected, briefly flash "RECONNECTED" so the engineer knows there was a drop and can assess if any critical data was missed.
QWebSockets vs SSE vs polling — when would you use each in an F1 context?▶
  • WebSockets — full-duplex, high-frequency telemetry during live sessions. Client can also send control messages (subscribe/unsubscribe to channels). The right choice for live race data.
  • SSE (Server-Sent Events) — server-push only, simpler, auto-reconnects. Good for pipeline status updates, session state changes (yellow flag, safety car), result notifications. Simpler to implement and debug than WebSockets for one-directional flows.
  • Polling — only when live data isn't needed and the source doesn't support push. Wind tunnel batch results, historical lap data loads. The simplicity is worth it when latency doesn't matter.
  • F1 split: WebSocket for all live telemetry channels; SSE for session status (track state, flag conditions, tyre strategy alerts); REST for historical data retrieval.

          <div key={vItem.key} style={{ position: 'absolute', top: vItem.start, height: vItem.size, width: '100%' }}>
            <LapRow lap={laps[vItem.index]} />
          </div>
        ))}
      </div>
    </div>
  )
}

Memory Management for Long Sessions

Cap Live Data Buffers

A 2-hour race at 200Hz = 1.44M points per channel. Keep the last N points in a circular buffer for the live view. Store the full dataset on the server — fetch historical ranges on demand.

Typed Arrays Over Object Arrays

Float64Array of 1M numbers uses ~8MB. An equivalent array of objects uses ~100MB+ (object overhead, GC pressure). Use typed arrays for all numeric time-series channels.

Lazy Load Heavy Charts

Load chart libraries (D3, heavy charting dependencies) only when the chart is in view. dynamic(() => import('./HeavyChart')) with IntersectionObserver. A dashboard with 10 charts shouldn't download all chart code upfront.

Cleanup on Unmount

Always close WebSockets, cancel pending fetches, clear intervals in useEffect cleanup. An engineer navigating between sessions must not accumulate background connections that consume bandwidth and CPU.

QHow do you profile and diagnose performance issues in a React data visualisation app?▶
  • React DevTools Profiler — identify which components re-render on every update and how long they take. Start here before guessing.
  • Chrome Performance panel — record a session, look for long tasks (>50ms) on the main thread. Usually find expensive transforms running synchronously on every render.
  • Why Did You Render — library that logs unnecessary re-renders with the props that changed. Invaluable for spotting missing memo() or unstable object references.
  • Memory panel — take heap snapshots before and after navigating between sessions. Detached DOM nodes or accumulating event listeners show up here.
  • Fix order: first eliminate unnecessary re-renders (memo, useMemo, useCallback), then move heavy computation to Web Workers, then switch SVG → Canvas for high-data-point renders, then profile again.

Q&A

QYou're handed a legacy web app built 6 years ago — no tests, jQuery, inline styles. How do you approach it?▶
  • Understand before touching. Run it, talk to the engineers who use it, understand what it does and what they rely on. The worst outcome is a rewrite that breaks something they depended on silently.
  • Don't rewrite first. Rewriting legacy code is almost always slower and riskier than incremental improvement. Rewrites lose institutional knowledge baked into the original code.
  • Add tests around the critical paths first. Characterisation tests — tests that document the current behaviour, not ideal behaviour. This gives you a safety net for any future change.
  • Identify the highest-value incremental improvements. Can I replace jQuery DOM manipulation with React for one component without touching the rest? Can I add TypeScript to the file I'm touching today?
  • Make it better than you found it, not perfect. The boy scout rule — leave the code cleaner than you found it, without a full rewrite blocking feature work.
QHow do you gather requirements from an Aerodynamics engineer who knows nothing about frontend development?▶
  • Ask about the job, not the software. "Walk me through what you do with this data" not "what features do you want in the UI?" They know their workflow — you discover the software requirements from that.
  • Show, don't ask. Bring a rough prototype or mockup. Engineers respond much better to a concrete thing they can react to than an abstract requirements conversation.
  • Ask about the current workaround. "What do you do today when you need to compare two CFD runs?" — the answer tells you exactly what the tool needs to replace.
  • Validate the data model early. "So you'd have one row per CFD run, and columns for each aero coefficient — does that match how you think about it?" Get this wrong and the whole UI is wrong.
  • Establish what "correct" means. For an Aero engineer, the chart being visually nice matters less than the numbers being right. Make sure you know what correct looks like before you ship.

Q&A

QWhat's the difference between a CFD run comparison tool and a telemetry viewer — and why does it matter for how you build them?▶

CFD data is batch, spatial, and relatively small — a run produces a fixed set of aero coefficients and surface maps. The key query is "compare run A against run B across a parameter sweep." This is a table + overlay chart problem. Data arrives once, no real-time stream.

Telemetry is time-series, high-frequency, and potentially live — 50+ channels at up to 200Hz per session. The key query is "show me speed and throttle overlaid for laps 23 and 31 across the S1 braking zone." This is a Canvas rendering problem with zoom/brush interaction. During a session, data streams in live.

They need different architectures: CFD is a standard React app with a comparison table and SVG overlay charts. Telemetry needs Canvas rendering, LTTB downsampling, Web Workers for processing, and WebSocket for live feeds. Conflating them leads to over-engineering one and under-engineering the other.

Architecture Decisions to Explain

State Architecture

  • URL params hold: selected lap IDs, active channel, zoom range — shareable
  • Zustand store holds: raw telemetry buffers, live data, session metadata
  • Derived data (downsampled points, delta trace) computed with useMemo
  • Live WebSocket data → useRef buffer → flushed to store at 10fps

Rendering Architecture

  • Canvas 2D for all high-point-count traces
  • SVG overlay for interactive markers, hover crosshair, zoom handles
  • Web Worker for LTTB downsampling — off main thread
  • Each trace is a separate Canvas layer — z-stacked with CSS
  • requestAnimationFrame loop for live trace updates

Flashcards
Quick-fire definitions and answers. Use these 30 minutes before the interview to prime your brain. Don't read them cold — think your own answer first, then reveal.

Core Concepts

?What is LTTB and when do you use it?▶
Largest-Triangle-Three-Buckets. A downsampling algorithm that preserves the visual shape of a time-series while reducing point count. Use it when you have millions of telemetry samples but a canvas width of only 1200px — there's no point rendering more points than pixels. Run in a Web Worker to avoid blocking the main thread.
?Canvas vs SVG — when does Canvas win?▶
Canvas wins when you have more than ~5,000 points or need animation at 60fps. SVG becomes a DOM bottleneck at scale. Canvas is a pixel buffer — once drawn, the browser doesn't care about individual elements. SVG wins when you need accessibility, CSS animations, or interactive per-element hover.
?Why align lap comparison by distance, not time?▶
Two laps take different amounts of time — the faster lap is shorter in duration. If you align by time, the traces are out of phase by the lap delta at every point. Aligning by distance along the circuit keeps both laps at the same physical location on the x-axis, so you can see where time is lost and gained.
?What is a discriminated union in TypeScript?▶
A union type where each member has a shared literal field (usually type or kind) that narrows the type in a switch/if block. { type: 'loaded'; data: T } | { type: 'error'; error: Error } — after checking state.type === 'loaded', TypeScript knows data exists.
?What's a circular buffer and why use it for telemetry?▶
A fixed-size array that overwrites the oldest entry when full. For live telemetry, you only want the last N seconds of data visible in the live view. A circular buffer means you never allocate more memory than needed and never need to shift the array (expensive for large arrays).
?Why use useRef instead of useState for a WebSocket buffer?▶
WebSocket messages can arrive 200 times per second. Every setState triggers a re-render. Storing incoming data in a useRef buffer and flushing to state at a capped rate (e.g. every 100ms) means React renders at ~10fps, not 200fps. The ref update is synchronous and doesn't trigger re-renders.
?What is a branded/nominal type in TypeScript?▶
TypeScript uses structural typing — two types with the same shape are interchangeable. A branded type adds a phantom field (_brand: 'Seconds') to make types nominally distinct. Prevents speed: Metres being passed as duration: Seconds — they're both number structurally, but the brand makes the compiler reject the swap.
?What is DPR and why does it matter for Canvas?▶
devicePixelRatio. On retina/HiDPI screens, 1 CSS pixel = 2+ physical pixels. If your Canvas element is 800px wide but you only draw at 800px resolution, it looks blurry. Fix: set canvas width/height to 800 * dpr, scale the context by dpr, but keep CSS size at 800px. Sharp on all displays.
?What is a Web Worker and what work should go there?▶
A background thread that can run JavaScript without blocking the main thread (and therefore the UI). Send it: CPU-heavy computation — LTTB downsampling of 500k telemetry points, parsing large binary buffers, statistical calculations. Don't send it: DOM manipulation (can't), state management, UI logic. Communicate via postMessage.
?Why encode complex state in the URL for internal tools?▶
Because engineers share results with colleagues. If the active laps, channel selection, and zoom range are in the URL, you can copy the address bar and send it — the recipient sees the exact same view. Without URL state, sharing requires screenshots or lengthy descriptions. Internal tools get enormous value from shareable, bookmarkable views.
