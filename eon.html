Architecture — Old vs New

Old Architecture

Bridge-based

  • JS thread ↔ Native thread communicate via an async JSON bridge
  • Bridge is a bottleneck — serialisation overhead on every call
  • Three threads: JS, Native UI, Shadow (layout)
  • Async-only bridge = animations can drop frames when JS thread is busy
New Architecture (default RN 0.73+)

JSI + Fabric + TurboModules

  • JSI: JS can hold direct reference to native objects — no bridge serialisation
  • Fabric: New rendering system — synchronous layout, supports concurrent React features
  • TurboModules: Native modules loaded lazily, called synchronously
  • Result: better performance, smaller startup time, Suspense support

React Native Interview Questions

QHow does React Native render UI compared to a web browser? Why does this matter for performance?▶
React Native doesn't use a WebView or the DOM. Instead it maps React components to actual native views — View → UIView on iOS, android.view.View on Android. This is why RN apps feel native, not webby.
  • Rendering pipeline: React runs on the JS thread → Yoga layout engine computes layout → native UI thread renders actual platform views
  • Performance implication: Anything that crosses the JS↔Native boundary has a cost. Heavy JS computation blocks the JS thread and can freeze animations — move animations to the UI thread with Reanimated.
  • New Architecture: Fabric removes the async bridge for rendering — layout is computed synchronously, enabling React concurrent features like Suspense and Transitions in RN.
QHow do you share code between React Native (mobile) and React (web) in the same codebase?▶
  • Business logic is fully shareable: TypeScript types, API clients, state management (Redux/Recoil), validation, date formatting — no platform dependencies
  • React Native Web: Compile RN components to web. Works well for simple components, less well for complex native UI. Shopify's Restyle and their React Native Web approach.
  • Platform file extensions: Button.native.tsx for RN, Button.web.tsx for web, Button.tsx as shared interface. Build tools pick the right one automatically.
  • Monorepo structure: packages/shared (types, API, state), apps/mobile (RN), apps/web (React). Turborepo manages the dependency graph.
  • At E.ON: Energy usage data formatting, billing calculations, user account state — all shareable. Charts might need platform-specific implementations (Victory Native vs Recharts).

QHow do you type a function that accepts different shapes based on a discriminant — for example, a bill component that renders differently per status?▶
Use a discriminated union on the props and let TypeScript narrow in each branch:
  • Define the union type with a common discriminant field (e.g. status)
  • The component receives the union type — TypeScript knows which fields are available in each case via narrowing
  • Use a switch on the discriminant — in each case branch TypeScript knows the exact shape
  • The exhaustive check pattern: add a default: assertNever(bill) so TypeScript errors if you add a new status and forget to handle it in the component

QWhat is the difference between server state and client state, and how do you manage each?▶
  • Server state: Lives on the server, fetched asynchronously. Has caching, staleness, and synchronisation concerns. Examples: energy usage data, bills, tariff details. Manage with TanStack Query — it handles caching, background refetch, loading/error states automatically.
  • Client state: Exists only in the app, doesn't need to sync with a server. Examples: selected date range, active tab, whether a modal is open, user preferences stored locally. Manage with Redux (global) or useState (local).
  • The mistake to avoid: Storing server data in Redux and manually managing caching. TanStack Query does this far better — let it own server state. Redux owns only client state.

// api/client.ts — base client with auth and error handling
class ApiClient {
  private baseURL: string

  async request<T>(path: string, options?: RequestInit): Promise<T> {
    const token = await getAuthToken()
    const res = await fetch(`${this.baseURL}${path}`, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${token}`,
        ...options?.headers,
      },
    })

    if (res.status === 401) { await refreshToken(); return this.request(path, options) }
    if (!res.ok) throw new ApiError(res.status, await res.json())
    return res.json() as Promise<T>
  }
}

QHow do you handle token refresh and retry in a React Native app without the user losing their session?▶
  • Proactive refresh: Store token expiry time. Before each request, check if within 60s of expiry — refresh proactively rather than waiting for a 401.
  • Reactive refresh: Intercept 401 responses. Trigger token refresh. Retry the original request with the new token.
  • Request queuing: If multiple requests get a 401 simultaneously, don't fire multiple refresh requests — queue them and resolve all after a single refresh. Use a flag and a promise queue.
  • Secure storage: Store refresh token in react-native-keychain (Keychain on iOS, Keystore on Android) — not AsyncStorage which is plaintext.
  • Final fallback: If refresh fails, clear tokens and navigate to login — never leave the user in a broken state.

What is the difference between ScrollView and FlatList? When do you use each?
ScrollView: Renders all children at once. Fine for short, fixed-size content (a form, a profile page). Terrible for long lists — it mounts and measures every item regardless of visibility, causing memory and performance problems.

FlatList: Virtualised — only renders items currently visible plus a small buffer. Use for any list of variable or unknown length. Rule of thumb: if it could have more than 20 items, use FlatList.

What is useSharedValue in Reanimated and why is it different from useState?
useSharedValue creates a value that lives on the UI thread, not the JS thread. Animations driven by shared values run at 60fps even when the JS thread is busy (processing data, re-rendering). useState causes a React re-render on every change — every frame of an animation would trigger a re-render and a bridge crossing. Shared values update on the UI thread without touching React.

How does deep linking work in React Native and why does it matter for push notifications?
Deep links are URLs that open a specific screen in the app — e.g. eon://bill/abc123. React Navigation's linking config maps URL patterns to screen names and params. Push notifications include a deep link URL in the payload — when tapped, the app opens and navigates directly to the relevant screen (e.g., a specific bill or alert). This is essential for good notification UX — not just opening the app home screen.

What is getItemLayout in FlatList and why does it improve performance?
Tells FlatList the exact height and offset of each item without measuring it. By default, FlatList measures item height as items come into view — expensive on initial render. With getItemLayout, FlatList knows the layout upfront so it can: scroll to any index instantly, pre-calculate which items are in the viewport, and skip layout measurement entirely. Only use it when items have a fixed, known height.

React & TypeScript

When does useCallback actually help performance vs just adding noise?
Only helps when: (1) The function is passed as a prop to a React.memo wrapped child — stable reference prevents unnecessary re-renders. (2) The function is a dependency in another hook's dependency array — stable reference prevents the hook from re-running.

Does NOT help when: The child doesn't use React.memo (it'll re-render anyway). The function is only used inside the component itself. Don't wrap everything in useCallback — the memoisation itself has a cost.

What is the difference between Redux Toolkit's createSlice and createAsyncThunk?
createSlice: Defines a slice of Redux state — the initial state, the reducer functions (synchronous state updates), and generates action creators automatically. It's for synchronous state changes.

createAsyncThunk: Handles async operations (API calls). Automatically dispatches pending/fulfilled/rejected actions. You handle these in your slice's extraReducers. The pattern: thunk does the async work, slice updates state based on the result.

What is the staleTime option in TanStack Query and how does it affect data fetching?
staleTime defines how long fetched data is considered fresh. While fresh, TanStack Query serves from cache and does NOT refetch on component mount or window focus. After staleTime expires, data is stale — the next mount or focus triggers a background refetch while still showing the stale data.

Default is 0 (always stale — refetch on every mount). For energy bills (rarely change): set high (5 min). For live usage data: set low or 0. Getting this right reduces unnecessary API calls significantly.

How do you securely store authentication tokens in React Native?
Use react-native-keychain — it stores secrets in the iOS Keychain and Android Keystore, both hardware-backed secure enclaves. Never use AsyncStorage for tokens — it's plaintext, accessible to any app on a rooted device, and may be backed up to cloud storage.

For access tokens (short-lived): can store in memory only (lost on app restart, user re-auths). For refresh tokens (long-lived): must use Keychain/Keystore. Add biometric protection for extra security on Keychain access.

QWhat is the never type and what are its practical uses?▶
never represents a value that can never exist — a type with no inhabitants.
  • Exhaustive checks: A function parameter typed as never must never be called. Use in the default of a switch — if TypeScript allows the call, you're missing a case.
  • Unreachable code: A function that always throws returns never — TypeScript knows subsequent code is unreachable.
  • Conditional filtering: T extends U ? T : never filters a union to only matching members — the never branches are collapsed out of the union.
  • Infinite loops: A function with an infinite loop also returns never.

  • Option 1 — Feature flag kill switch (fastest): If the broken feature is behind a flag, turn it off. Zero delay, no release needed. This is why you ship with flags.
  • Option 2 — OTA update with EAS Update / CodePush: If the fix is JS-only (no native code changes), push an OTA update. Users get it on next app launch without going through the App Store. Takes minutes.
  • Option 3 — Expedited App Store Review: Apple has an expedited review process for critical bugs. Submit with justification — they can review within hours instead of days. Not guaranteed.
  • Option 4 — Force update gate: If the bug makes the app unusable, show a forced update screen (your current version has a critical issue, please update). Requires a new build to already be in the store.
  • Prevention: The reason you have staged rollouts, monitoring, and feature flags — to catch and contain before it reaches all users.

Q&A

Why is flexDirection column by default in React Native but row on web?+

Mobile UIs are primarily vertical scroll lists — stacking children top-to-bottom is almost always what you want. Changing the default to column eliminates the most common manual override. On web, inline content flows horizontally, so row makes more sense. You still use row frequently in RN for header bars, button rows, and icon-label combos — it's just not the default.

What does StyleSheet.create actually do at runtime?+

In DEV mode it validates style properties and values, giving you errors for unknown CSS-style properties. In both modes it registers styles and returns numeric IDs — these IDs are sent over the bridge (or via JSI on New Architecture) instead of the full style objects, reducing serialisation overhead. It also allows native code to cache and reuse style objects. For New Architecture with Fabric, styles are processed entirely on the JS side via C++ bindings, but the create pattern still serves as a useful validation and organisation tool.

How do you handle safe area insets on iPhone notch / Dynamic Island?+
import { useSafeAreaInsets } from 'react-native-safe-area-context';

function Screen() {
  const insets = useSafeAreaInsets();
  return (
    <View style={{ flex: 1, paddingTop: insets.top, paddingBottom: insets.bottom }}>
      ...
    </View>
  );
}

// Or declaratively:

  return <SafeAreaView style={{ flex: 1 }} edges={['top', 'bottom']}>...</SafeAreaView>;
}
// Wrap the whole app in <SafeAreaProvider> in App.tsx

Never hardcode top/bottom padding — the Dynamic Island and Android gesture bar change the values. The edges prop lets you apply insets selectively (e.g., skip bottom inset inside a tab bar that handles it already).

How do you build a responsive layout without media queries?+

Use useWindowDimensions() to get live width/height that updates on rotation. Derive column counts, card widths, and font scales from those numbers. For font scaling respect the user's system font size setting via Text allowFontScaling (on by default) or set a max via maxFontSizeMultiplier. For tablets, break at a width threshold (commonly 768dp). Avoid Dimensions.get at module level as it won't react to orientation changes.

How does the shadow API differ between iOS and Android?+

iOS supports the full shadow* property set (shadowColor, shadowOffset, shadowOpacity, shadowRadius). Android uses a single elevation integer — it derives its own shadow from the theme's shadow colour (always dark). You can't control the shadow colour on Android without using a third-party library or a custom native view. Use Platform.select to write both in the same StyleSheet object.

When would you use Animated.Value vs react-native-reanimated?+

Use Animated API for simple, one-shot animations where you need to stay dependency-light (loading spinners, fade-ins). Use Reanimated 2/3 for anything gesture-driven, complex, or performance-critical — it runs animations entirely on the UI thread via worklets, eliminating bridge round-trips. Reanimated is the standard for swipe-to-dismiss, parallax scrolling, and shared element transitions. At senior level, the expected answer is: Reanimated for anything the user interacts with directly.

React Native Depth

The app's JS bundle takes 4 seconds to parse on a mid-range Android. What do you do?+

Diagnose first: use react-native-bundle-visualizer or metro-bundle-analyzer to find what's large. Common culprits: moment.js, lodash (import all), large image assets bundled as requires.

Fix options in order of impact: (1) Enable Hermes — it pre-compiles JS to bytecode at build time, eliminating parse time entirely at runtime. This is the single biggest win. (2) Code split with inline requires / lazy imports — React Navigation does this for screens. (3) Remove large deps (replace moment with date-fns tree-shaken, lodash with individual packages). (4) Enable RAM bundles for older RN apps that can't yet use Hermes. (5) Defer non-critical initialisation behind InteractionManager.runAfterInteractions.

Your React Native app works perfectly on iOS but crashes on a Samsung Galaxy A12. How do you debug it?+

Step 1: Reproduce with Flipper or adb logcat — Android-specific crashes often surface in the native log with a stack trace that doesn't appear in the Metro console. Step 2: Check for overflow:hidden clipping, elevation issues, or gradient/Animated APIs that behave differently on low-end GPUs. Step 3: Look at the A12 spec — 3–4GB RAM, older Exynos GPU. Suspect: OOMKilled (too many large images in FlatList), a missing enableSoftwareKeyboardHandling, or a native module that assumes a newer Android API level. Step 4: Test on Android emulator set to "Low RAM device" in AVD settings. Step 5: Sentry + Crashlytics — check if this device/OS combo is in the crash report's top entries.

Explain the React Native rendering pipeline end-to-end under the New Architecture.+

Under New Architecture (Fabric + TurboModules + JSI): (1) React runs a reconciliation pass on the JS thread, producing a React Element tree. (2) The Fabric renderer (replaces the old UIManager) generates a Shadow Node tree on the JS thread via JSI — no bridge serialisation. (3) Yoga (the layout engine) runs on the C++ Shadow tree to calculate layout (positions, sizes). (4) A committed tree is sent to the native UI thread, which creates or mutates native views. Key improvements vs Old Architecture: synchronous layout queries (no async round-trip), concurrent rendering support (React 18 features work properly), and direct C++ function calls instead of JSON-over-bridge for all native calls.

How would you implement offline support for energy meter readings?+
// Strategy: read-through cache + optimistic writes + sync queue
// 1. On fetch: load from SQLite/MMKV first, show immediately,
//    then fetch from API and update if changed
// 2. On mutation (manual reading submission): write to local queue,
//    attempt API, if offline keep in queue

import NetInfo from '@react-native-community/netinfo';
import { MMKV } from 'react-native-mmkv';

const storage = new MMKV();
const QUEUE_KEY = 'offline_queue';

async function submitReading(reading: MeterReading) {
  const { isConnected } = await NetInfo.fetch();
  if (isConnected) {
    return api.postReading(reading);
  }
  // Queue for later
  const queue = JSON.parse(storage.getString(QUEUE_KEY) ?? '[]');
  queue.push({ type: 'SUBMIT_READING', payload: reading, timestamp: Date.now() });
  storage.set(QUEUE_KEY, JSON.stringify(queue));
  // Show optimistic success to user
}

// On app foreground / connectivity restore:
async function drainQueue() {
  const queue = JSON.parse(storage.getString(QUEUE_KEY) ?? '[]');
  for (const item of queue) {
    await api.postReading(item.payload); // retry with exponential backoff
  }
  storage.delete(QUEUE_KEY);
}

For energy data specifically: meter readings are append-only and idempotent by reading timestamp — safe to retry. Flag queued items in the UI with a "pending sync" indicator.

Architecture & Design Decisions

When would you NOT use Redux at a senior level?+

Redux is justified for: complex cross-cutting state, time-travel debugging needs, large teams where state traceability matters. You would not use Redux when: all state is server-derived (use TanStack Query instead — it handles caching, revalidation, optimistic updates out of the box), the app is small enough that Context + useReducer suffices, or the team is small and the boilerplate overhead costs more than the benefits. The senior answer: "I reach for TanStack Query for server state and Context/Zustand for lightweight UI state. Redux earns its keep when I need cross-feature state with complex update logic or when I have explicit replay/undo requirements."

How do you handle breaking API changes from the backend team without breaking the mobile app for users who haven't updated?+

Short answer: API versioning + a BFF layer + feature flags. In practice: (1) Never remove a field — deprecate and keep it populated. (2) If you must break, version the endpoint (/api/v2/readings) and keep v1 alive until your minimum supported app version is past the breaking change. (3) Use a BFF (Backend For Frontend) to normalise API responses — the mobile app talks to the BFF, which handles v1→v2 translation. (4) Use feature flags (LaunchDarkly / Firebase Remote Config) to gate new API calls behind a flag — you can roll forward and back without a new app release. (5) For OTA updates (Expo EAS Update), you can push JS fixes to ~95% of users within 24 hours for non-breaking regressions.

You're asked to reduce the app's bundle size by 30%. Walk me through your process.+

1. Measure first — run npx react-native-bundle-visualizer to get a treemap of what's in the bundle. 2. Low-hanging fruit: switch full lodash/moment imports to tree-shaken alternatives (lodash-es, date-fns). One import of moment adds ~67KB minified. 3. Image audit — large PNGs bundled with require() inflate JS bundle. Move to dynamic requires or remote URLs. Use WebP format (30-40% smaller than PNG). 4. Code splitting — React Navigation lazy-loads screens by default. Ensure large screens not in the initial tab are lazy. 5. Hermes — if not already on, enables bytecode which removes the raw JS from the bundle. 6. Remove unused libraries — check package.json for deps that aren't referenced. 7. Inline requires for heavy imports used only occasionally (charts, PDF generators).

How would you build a design system that works across React Native and React web?+

Use a monorepo (Turborepo/Nx). Create a packages/tokens package: colours, spacing, typography, radii — plain JS/TS, no framework dependency. Create packages/hooks: shared logic hooks that work in both environments (useDebounce, useWindowSize, business logic). Keep UI components platform-specific: packages/ui-native and packages/ui-web — they import from tokens but render platform-appropriate primitives (View/Text vs div/p). The key insight: share logic, not markup. Attempting to share a single component tree between RN and web via react-native-web works for simple cases but becomes a maintenance burden for complex interactive components with platform-specific behaviour.

What's the difference between unknown and any, and when does it matter for an energy app?+

any disables type checking entirely — you can call methods on it, pass it anywhere, and TS won't complain. unknown is the type-safe alternative: you must narrow it before you can use it. In an energy app, API responses from meter APIs should be typed as unknown at the boundary, then parsed through a validation schema (Zod) before use. Using any for API data means a backend contract change silently breaks your UI — the tariff object that used to have unit_rate_inc_vat now has unitRateIncVat and you find out at runtime when the bill calculation returns NaN.

Production & Incident Handling

The Sentry crash rate spikes to 8% on the morning of a smart meter billing run. Walk me through your response.+

Immediate (0–5 min): Open Sentry, filter by the spike time window, group by issue. Identify top crash — look at the stack trace, affected device/OS distribution, and breadcrumbs leading to it. 5–15 min: If it's a JS error, check if an OTA (EAS Update) was deployed overnight — roll it back immediately if so. If it's a native crash, check if a backend API changed its response shape. 15–30 min: Communicate status to stakeholders (PM, backend lead). If crash rate is sustained >5%, consider a forced update prompt or disabling the affected feature via remote config. Root cause: Billing run likely returns a different data shape for accounts with smart meters vs SMETS1. Probably a null/undefined access on a field that exists on some accounts but not all. Fix: add optional chaining + Zod validation at the API layer. Deploy OTA fix. Post-incident: Write a 5-minute blameless RCA. Add a test case for the null path. Add a Sentry alert for crash rate >2%.

Key phrase to use: "I treated it as a two-way door decision" (reversible) or "I recognised this was hard to undo, so I spent X days de-risking it before committing."

Give an example of a time you improved the development process for your team.+

What they're assessing: Proactive ownership, systems thinking, whether you leave a team better than you found it — crucial for a 6-month contract.

Strong answer signals: You spotted a recurring pain point (slow CI, no shared types, inconsistent code review, missing error monitoring), proposed a solution, built buy-in, implemented it, and measured the improvement.

Example angles: Setting up Sentry + source maps for a team that was debugging from user reports. Adding Zod schemas at API boundaries to catch contract drift. Writing a PR template that reduced review time. Adding Storybook/component docs that reduced design-dev misalignment.

Quantify: "PR review cycles dropped from 3 rounds to 1.5 on average" or "We went from 2 production bugs per sprint to 0 for the following quarter."

Tell me about a time you had to refactor a large piece of legacy code. How did you approach it?+

What they're assessing: Patience, risk management, ability to balance delivery with improvement — not just rewriting things for fun.

Strong answer signals: You didn't rewrite everything at once. You used the strangler fig pattern — wrap the old thing, replace piece by piece, keep tests green throughout. You had a clear exit criterion before starting.

Key phrases: "Characterisation tests first — I wrote tests against the existing behaviour before touching anything, so I had a safety net." "I defined what 'done' looked like before writing a line."

What to avoid: "I convinced the team to do a full rewrite" — this is almost always a red flag in an enterprise context.

Collaboration & Communication

Tell me about a time you disagreed with a colleague or manager about a technical approach. How did you handle it?+

What they're assessing: Psychological safety, professionalism, whether you push back constructively or just comply/explode.

Strong answer signals: You made your case with evidence (benchmarks, industry precedent, failure scenarios). You listened to their reasoning. You reached a decision together — or deferred to their call with clear documentation of your concern. You didn't relitigate after the decision was made.

Framework: "Disagree and commit" — once a decision is made, you execute it fully, but you might add "I'd like to revisit this in 4 weeks to see if my concern materialised."

Topics that work well: Choice of library, migration timing, test coverage standards, TypeScript strictness level.

Describe a time you had to communicate a technical problem to a non-technical stakeholder.+

What they're assessing: Communication skills, empathy, ability to translate technical risk into business impact — especially important at a large utility like E.ON where product and business stakeholders are non-technical.

Structure your answer: What was the technical issue? What was the business impact? How did you frame it without jargon? What decision did you enable them to make?

Example frame: "I stopped talking about 'memory leaks' and started talking about 'the app crashing for 1 in 12 users trying to view their bill — and here's the customer complaint trend to show it.' That framing got the sprint priority changed in 10 minutes."

Tell me about a time you mentored or helped a junior developer grow.+

What they're assessing: Leadership potential, patience, investment in team health. Even as a contractor, demonstrating this shows you'll be a force multiplier.

Strong answer signals: You didn't just give them the answer — you asked questions to help them figure it out. You gave specific, actionable code review feedback rather than vague comments. You made time for 1:1s or pairing sessions.

Specific examples work better than general ones: "I noticed their PRs always had the same issue — no error handling at API boundaries. Instead of flagging it each time, I paired with them for an hour and we wrote the pattern together. Their next 5 PRs had it right."

Problem Solving & Resilience

Tell me about a significant bug you found in production. What happened and what did you do?+

What they're assessing: Ownership, composure under pressure, structured debugging, blameless post-mortem mindset.

Structure: How you detected it (Sentry / user report / monitoring). How you triaged and scoped impact. What immediate mitigation you applied (feature flag off / rollback / hotfix). Root cause investigation. Permanent fix. What you changed to prevent recurrence.

Key signal: "I didn't point fingers — I focused on the system failure, not the person. We updated the runbook and added a regression test."

Quantify impact: "It affected ~200 users for 47 minutes. We issued a proactive in-app notification and logged the incident."

Tell me about a project that didn't go as planned. What did you learn?+

What they're assessing: Self-awareness, growth mindset, honesty. This is not a trick question — everyone has failures. The quality of your reflection matters more than the nature of the failure.

Strong answer structure: What was planned → what went wrong → what you did about it → what you'd do differently → what you actually changed in your approach since.

Authenticity beats perfection: "I underestimated the complexity of the migration and committed to a deadline without a spike. I missed the date by two weeks. Since then I always insist on a spike before estimating any migration work."

Avoid: Blaming the team, the PM, the product — own your part in it.

Why are you interested in this contract specifically, and what will you bring in the first 30 days?+

What they're assessing: Motivation fit, self-awareness, planning ability. For a 6-month contract the ramp-up time matters — they want someone who hits the ground running.

Interest: Mention something specific — the React Native + web stack (genuine breadth), the domain (energy data / smart meters is genuinely interesting engineering), the scale (millions of customers means production engineering matters).

First 30 days answer (the 30-60-90 framework):

Days 1–30: Listen and learn — understand the codebase, the CI/CD pipeline, the team's conventions. Ship small PRs to build context. Ask "why" before suggesting "what if". Map the biggest pain points the team mentions in passing.

Days 30–60: Deliver a meaningful feature end-to-end. Contribute to architectural discussions with evidence, not opinion.

Days 60–90+: Identify one systemic improvement (tooling, testing, documentation) and propose it. Start unblocking others, not just delivering my own work.
