New Architecture vs Old Architecture React Native's new architecture (JSI, Fabric, TurboModules) is now the default in RN 0.73+. Know the difference — interviewers at senior level will ask about this.

Architecture — Old vs New

Old Architecture

Bridge-based

  • JS thread ↔ Native thread communicate via an async JSON bridge
  • Bridge is a bottleneck — serialisation overhead on every call
  • Three threads: JS, Native UI, Shadow (layout)
  • Async-only bridge = animations can drop frames when JS thread is busy
New Architecture (default RN 0.73+)

JSI + Fabric + TurboModules

  • JSI: JS can hold direct reference to native objects — no bridge serialisation
  • Fabric: New rendering system — synchronous layout, supports concurrent React features
  • TurboModules: Native modules loaded lazily, called synchronously
  • Result: better performance, smaller startup time, Suspense support

React Native Interview Questions

QHow does React Native render UI compared to a web browser? Why does this matter for performance?▶
React Native doesn't use a WebView or the DOM. Instead it maps React components to actual native views — View → UIView on iOS, android.view.View on Android. This is why RN apps feel native, not webby.
  • Rendering pipeline: React runs on the JS thread → Yoga layout engine computes layout → native UI thread renders actual platform views
  • Performance implication: Anything that crosses the JS↔Native boundary has a cost. Heavy JS computation blocks the JS thread and can freeze animations — move animations to the UI thread with Reanimated.
  • New Architecture: Fabric removes the async bridge for rendering — layout is computed synchronously, enabling React concurrent features like Suspense and Transitions in RN.
QHow do you share code between React Native (mobile) and React (web) in the same codebase?▶
  • Business logic is fully shareable: TypeScript types, API clients, state management (Redux/Recoil), validation, date formatting — no platform dependencies
  • React Native Web: Compile RN components to web. Works well for simple components, less well for complex native UI. Shopify's Restyle and their React Native Web approach.
  • Platform file extensions: Button.native.tsx for RN, Button.web.tsx for web, Button.tsx as shared interface. Build tools pick the right one automatically.
  • Monorepo structure: packages/shared (types, API, state), apps/mobile (RN), apps/web (React). Turborepo manages the dependency graph.
  • At E.ON: Energy usage data formatting, billing calculations, user account state — all shareable. Charts might need platform-specific implementations (Victory Native vs Recharts).

// Custom hook — fetches energy usage for a date range
function useEnergyUsage(period: 'day' | 'week' | 'month') {
  const [data, setData] = useState<UsageData | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<Error | null>(null)

  useEffect(() => {
    let cancelled = false
    setLoading(true)

    api.getUsage(period)
      .then(d => { if (!cancelled) { setData(d); setLoading(false) } })
      .catch(e => { if (!cancelled) { setError(e); setLoading(false) } })

    return () => { cancelled = true }  // cleanup — prevent setState on unmounted
  }, [period])

  return { data, loading, error }
}

QHow do you type a function that accepts different shapes based on a discriminant — for example, a bill component that renders differently per status?▶
Use a discriminated union on the props and let TypeScript narrow in each branch:
  • Define the union type with a common discriminant field (e.g. status)
  • The component receives the union type — TypeScript knows which fields are available in each case via narrowing
  • Use a switch on the discriminant — in each case branch TypeScript knows the exact shape
  • The exhaustive check pattern: add a default: assertNever(bill) so TypeScript errors if you add a new status and forget to handle it in the component

What I'd Recommend for E.ON's React Native App Redux Toolkit + TanStack Query. RTK for global client state (auth, user account, preferences). TanStack Query for all server data (usage, bills, tariff). This is the industry standard pattern for enterprise apps — clear separation, excellent DevTools, battle-tested.

export const fetchAccount = createAsyncThunk(
  'account/fetch',

    try { return await api.getAccount(accountId) }
    catch (err) { return rejectWithValue('Failed to load account') }

const accountSlice = createSlice({
  name: 'account',
  initialState: { profile: null, tariff: null, status: 'idle', error: null } as AccountState,
  reducers: {
    updatePreferences(state, action: PayloadAction<Partial<UserPreferences>>) {
      if (state.profile) Object.assign(state.profile.preferences, action.payload)
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchAccount.pending, (state) => { state.status = 'loading' })
      .addCase(fetchAccount.fulfilled, (state, action) => {
        state.status = 'succeeded'
        state.profile = action.payload.profile
        state.tariff = action.payload.tariff
      })
      .addCase(fetchAccount.rejected, (state, action) => {
        state.status = 'failed'
        state.error = action.payload as string
      })
  }
})

export const selectTariff = (state: RootState) => state.account.tariff
QWhat is the difference between server state and client state, and how do you manage each?▶
  • Server state: Lives on the server, fetched asynchronously. Has caching, staleness, and synchronisation concerns. Examples: energy usage data, bills, tariff details. Manage with TanStack Query — it handles caching, background refetch, loading/error states automatically.
  • Client state: Exists only in the app, doesn't need to sync with a server. Examples: selected date range, active tab, whether a modal is open, user preferences stored locally. Manage with Redux (global) or useState (local).
  • The mistake to avoid: Storing server data in Redux and manually managing caching. TanStack Query does this far better — let it own server state. Redux owns only client state.

// FlatList — virtualised, only renders visible items
function BillingHistory({ bills }: { bills: Bill[] }) {

      renderItem={renderItem}

    />
  )
}

// api/client.ts — base client with auth and error handling
class ApiClient {
  private baseURL: string

  async request<T>(path: string, options?: RequestInit): Promise<T> {
    const token = await getAuthToken()
    const res = await fetch(`${this.baseURL}${path}`, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        Authorization: `Bearer ${token}`,
        ...options?.headers,
      },
    })

    if (res.status === 401) { await refreshToken(); return this.request(path, options) }
    if (!res.ok) throw new ApiError(res.status, await res.json())
    return res.json() as Promise<T>
  }
}

// api/energy.ts — typed endpoint wrappers
export const energyApi = {

QHow do you handle token refresh and retry in a React Native app without the user losing their session?▶
  • Proactive refresh: Store token expiry time. Before each request, check if within 60s of expiry — refresh proactively rather than waiting for a 401.
  • Reactive refresh: Intercept 401 responses. Trigger token refresh. Retry the original request with the new token.
  • Request queuing: If multiple requests get a 401 simultaneously, don't fire multiple refresh requests — queue them and resolve all after a single refresh. Use a flag and a promise queue.
  • Secure storage: Store refresh token in react-native-keychain (Keychain on iOS, Keystore on Android) — not AsyncStorage which is plaintext.
  • Final fallback: If refresh fails, clear tokens and navigate to login — never leave the user in a broken state.

QWhat do you look for in a code review?▶
I review in layers — correctness first, then quality:
  • Correctness: Does it do what the ticket says? Edge cases handled? Error states?
  • Type safety: No any, no non-null assertions without reason, proper nullability handling
  • Performance: Unnecessary re-renders? Missing useCallback/useMemo on expensive operations? FlatList used for long lists?
  • Accessibility: Are interactive elements labelled? Can they be used with a screen reader?
  • Security: Sensitive data not logged? Tokens not stored in plaintext?
  • Tests: Are they testing behaviour, not implementation? Do they cover the failure path?
  • Tone: I write review comments as questions or suggestions, not commands. "Could this be simplified with useMemo?" not "This is wrong".

React Native

What is the difference between ScrollView and FlatList? When do you use each?
ScrollView: Renders all children at once. Fine for short, fixed-size content (a form, a profile page). Terrible for long lists — it mounts and measures every item regardless of visibility, causing memory and performance problems.

FlatList: Virtualised — only renders items currently visible plus a small buffer. Use for any list of variable or unknown length. Rule of thumb: if it could have more than 20 items, use FlatList.

What is useSharedValue in Reanimated and why is it different from useState?
useSharedValue creates a value that lives on the UI thread, not the JS thread. Animations driven by shared values run at 60fps even when the JS thread is busy (processing data, re-rendering). useState causes a React re-render on every change — every frame of an animation would trigger a re-render and a bridge crossing. Shared values update on the UI thread without touching React.

How does deep linking work in React Native and why does it matter for push notifications?
Deep links are URLs that open a specific screen in the app — e.g. eon://bill/abc123. React Navigation's linking config maps URL patterns to screen names and params. Push notifications include a deep link URL in the payload — when tapped, the app opens and navigates directly to the relevant screen (e.g., a specific bill or alert). This is essential for good notification UX — not just opening the app home screen.

What is getItemLayout in FlatList and why does it improve performance?
Tells FlatList the exact height and offset of each item without measuring it. By default, FlatList measures item height as items come into view — expensive on initial render. With getItemLayout, FlatList knows the layout upfront so it can: scroll to any index instantly, pre-calculate which items are in the viewport, and skip layout measurement entirely. Only use it when items have a fixed, known height.

React & TypeScript

When does useCallback actually help performance vs just adding noise?
Only helps when: (1) The function is passed as a prop to a React.memo wrapped child — stable reference prevents unnecessary re-renders. (2) The function is a dependency in another hook's dependency array — stable reference prevents the hook from re-running.

Does NOT help when: The child doesn't use React.memo (it'll re-render anyway). The function is only used inside the component itself. Don't wrap everything in useCallback — the memoisation itself has a cost.

What is the difference between Redux Toolkit's createSlice and createAsyncThunk?
createSlice: Defines a slice of Redux state — the initial state, the reducer functions (synchronous state updates), and generates action creators automatically. It's for synchronous state changes.

createAsyncThunk: Handles async operations (API calls). Automatically dispatches pending/fulfilled/rejected actions. You handle these in your slice's extraReducers. The pattern: thunk does the async work, slice updates state based on the result.

What is the staleTime option in TanStack Query and how does it affect data fetching?
staleTime defines how long fetched data is considered fresh. While fresh, TanStack Query serves from cache and does NOT refetch on component mount or window focus. After staleTime expires, data is stale — the next mount or focus triggers a background refetch while still showing the stale data.

Default is 0 (always stale — refetch on every mount). For energy bills (rarely change): set high (5 min). For live usage data: set low or 0. Getting this right reduces unnecessary API calls significantly.

How do you securely store authentication tokens in React Native?
Use react-native-keychain — it stores secrets in the iOS Keychain and Android Keystore, both hardware-backed secure enclaves. Never use AsyncStorage for tokens — it's plaintext, accessible to any app on a rooted device, and may be backed up to cloud storage.

For access tokens (short-lived): can store in memory only (lost on app restart, user re-auths). For refresh tokens (long-lived): must use Keychain/Keystore. Add biometric protection for extra security on Keychain access.

QHow would you architect a feature — say, smart meter energy usage dashboard — from design to production?▶
Full senior answer — walk through each layer:
  • 1. Requirements clarity: What granularity? Hourly/daily/monthly. What devices? Which API? What's the loading state and empty state?
  • 2. Types first: Define UsagePoint, UsagePeriod, API response shape in packages/shared/types
  • 3. API layer: Add typed endpoint to the shared API client. Write the Zod schema to validate the response.
  • 4. Data hook: useEnergyUsage(period) in shared package — TanStack Query, typed, handles loading/error/refetch
  • 5. Chart component: Platform-specific — Victory Native on mobile, Recharts on web. Shared data-transform utility to format API data into chart series.
  • 6. Screen/Page: Compose the hook + chart + period selector + error boundary. Feature-flag the new screen for staged rollout.
  • 7. Tests: Unit test the data-transform utility. RNTL test for the component with mocked hook. E2E test for the golden path.
  • 8. Performance: Is the chart lazy-loaded? useMemo on data transforms? Tested on low-end Android?
QYou join and find no monorepo — web and mobile are separate repos duplicating types and API logic. How do you fix this without breaking delivery?▶
  • Assess before acting. Understand how diverged they are — same types, same API client? Or different patterns entirely?
  • Don't do a big-bang migration. That's months of work with no user value and a high breakage risk on a 6-month contract.
  • Start with a shared package for new code. Create a shared npm package (or monorepo workspace). New types and utilities go there from day 1.
  • Migrate opportunistically. When touching existing code, extract the type/utility to the shared package. Don't touch code you're not already working in.
  • Align the team first. Share the approach and get buy-in before changing the repo structure. Architectural changes affect everyone.
  • Measure: Track how many imports come from the shared package over time — shows momentum without blocking delivery.

Conditional Types

// Conditional types — type depends on another type
type NonNullable<T> = T extends null | undefined ? never : T

// Extract items from a union that match a condition
type PaidBills = Extract<Bill, { status: 'paid' }>
type UnpaidBills = Exclude<Bill, { status: 'paid' }>

// Infer — extract type from inside another type
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T
type ApiResult = UnwrapPromise<ReturnType<typeof energyApi.getUsage>>
// ^ gets the resolved value type of an async function without calling it

// Deep readonly — prevent mutation at any level
type DeepReadonly<T> = T extends (infer U)[]
  ? ReadonlyArray<DeepReadonly<U>>
  : T extends object
  ? { readonly [K in keyof T]: DeepReadonly<T[K]> }
  : T

type ImmutableUsageData = DeepReadonly<UsagePoint<'daily'>[]>

Mapped Types & Template Literal Types

// Mapped types — transform every key in a type
type Optional<T> = { [K in keyof T]?: T[K] }
type Nullable<T> = { [K in keyof T]: T[K] | null }

// Key remapping — prefix all keys
type Prefixed<T, P extends string> = {
  [K in keyof T as `${P}${Capitalize<string & K>}`]: T[K]
}
type PrefixedBill = Prefixed<{ amount: number; dueDate: string }, 'bill'>
// → { billAmount: number; billDueDate: string }

// Template literal types — for event names, action types, routes

// Builder pattern with type inference — fluent API query builder
class UsageQuery<T extends Partial<UsageQueryParams> = {}> {
  constructor(private params: T = {} as T) {}

  period<P extends Period>(p: P) {
    return new UsageQuery<T & { period: P }>({ ...this.params, period: p })
  }
  granularity<G extends Granularity>(g: G) {
    return new UsageQuery<T & { granularity: G }>({ ...this.params, granularity: g })
  }
  // build() only available when both period AND granularity are set
  build(this: UsageQuery<T & { period: Period; granularity: Granularity }>) {
    return this.params
  }
}

const query = new UsageQuery()
  .period('month')
  .granularity('daily')
  .build()  // ✓ compiles

// Exhaustive switch — fails to compile if a union case is unhandled
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${x}`)
}

function getBillColour(bill: Bill): string {
  switch (bill.status) {
    case 'pending': return 'grey'
    case 'issued':  return 'blue'
    case 'paid':    return 'green'
    case 'overdue': return 'red'
    default: return assertNever(bill)  // add new status → compile error here
  }
}
QWhat is the never type and what are its practical uses?▶
never represents a value that can never exist — a type with no inhabitants.
  • Exhaustive checks: A function parameter typed as never must never be called. Use in the default of a switch — if TypeScript allows the call, you're missing a case.
  • Unreachable code: A function that always throws returns never — TypeScript knows subsequent code is unreachable.
  • Conditional filtering: T extends U ? T : never filters a union to only matching members — the never branches are collapsed out of the union.
  • Infinite loops: A function with an infinite loop also returns never.

// react-native-keychain — hardware-backed secure storage
import * as Keychain from 'react-native-keychain'

export const tokenStorage = {
  async save(accessToken: string, refreshToken: string) {
    await Keychain.setGenericPassword('eon_tokens', JSON.stringify({ accessToken, refreshToken }), {
      accessControl: Keychain.ACCESS_CONTROL.BIOMETRY_CURRENT_SET_OR_DEVICE_PASSCODE,
      accessible: Keychain.ACCESSIBLE.WHEN_UNLOCKED_THIS_DEVICE_ONLY,
      // WHEN_UNLOCKED_THIS_DEVICE_ONLY — not backed up to iCloud
    })
  },

  async get() {
    const credentials = await Keychain.getGenericPassword()
    if (!credentials) return null
    return JSON.parse(credentials.password) as { accessToken: string; refreshToken: string }
  },

  async clear() {
    await Keychain.resetGenericPassword()
  }
}

QA user reports they can see another user's account data in the app. What do you do?▶
  • Treat as P1 immediately. Account data exposure is a GDPR breach with a 72-hour reporting window to the ICO.

QHow do you make an energy usage chart accessible to a blind user?▶
Charts are inherently visual — screen readers can't interpret a rendered SVG or canvas meaningfully. Solutions:
  • Accessible description: Wrap the chart in a View with a comprehensive accessibilityLabel — "Bar chart showing daily electricity usage for May 2024. Highest usage was 15 kWh on May 14th. Average usage was 9.2 kWh per day."
  • Data table alternative: Add a "View as table" toggle — same data in a FlatList of rows, fully accessible
  • Key insights in text: Always render the headline numbers as text below the chart — "You used 285 kWh this month, 12% less than last month." Screen readers get this for free.
  • Hide chart from AT: Set accessibilityElementsHidden={true} on the chart container — the data is in the description and table, not the visual.

CI/CD & Release Process
Mobile CI/CD is significantly harder than web — app store reviews, code signing, OTA updates, multiple environments. A senior engineer understands the full release pipeline.

The Mobile Release Challenge vs Web

Web

Ship anytime

  • Deploy in seconds — no gatekeeper
  • Instant rollback — revert the deploy
  • All users on latest version immediately
  • Feature flags for instant on/off
Mobile

App store gating

  • iOS App Store review: 24–72 hours
  • Users on old versions for months — must maintain backwards compatibility
  • Code signing — provisioning profiles, certificates
  • OTA updates (CodePush / EAS Update) — JS-only changes without store review

Environments & Feature Flags

Environment Strategy

  • development — local dev, mock APIs or dev backend
  • staging — full backend integration, TestFlight / internal track
  • production — App Store / Play Store, real users
  • Separate app IDs per environment on iOS — can install all three simultaneously
  • Environment-specific bundle IDs, API URLs, and analytics keys

Feature Flags on Mobile

  • Use LaunchDarkly or PostHog feature flags — toggle features without a release
  • Ship features dark — code deployed, flag off, no users see it
  • Gradual rollout — 5% → 20% → 50% → 100%
  • Kill switch — turn off a broken feature without an app store release
  • Essential for a consumer app at E.ON's scale — can't push a hotfix to 1M users instantly
QA critical bug is in production affecting all users on iOS. What are your options?▶
  • Option 1 — Feature flag kill switch (fastest): If the broken feature is behind a flag, turn it off. Zero delay, no release needed. This is why you ship with flags.
  • Option 2 — OTA update with EAS Update / CodePush: If the fix is JS-only (no native code changes), push an OTA update. Users get it on next app launch without going through the App Store. Takes minutes.
  • Option 3 — Expedited App Store Review: Apple has an expedited review process for critical bugs. Submit with justification — they can review within hours instead of days. Not guaranteed.
  • Option 4 — Force update gate: If the bug makes the app unusable, show a forced update screen (your current version has a critical issue, please update). Requires a new build to already be in the store.
  • Prevention: The reason you have staged rollouts, monitoring, and feature flags — to catch and contain before it reaches all users.

Production Error Tracking — Sentry for RN

// sentry setup — captures native crashes AND JS errors
import * as Sentry from '@sentry/react-native'

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  environment: process.env.APP_ENV,          // 'staging' | 'production'
  tracesSampleRate: 0.1,                   // 10% of sessions traced
  enableNative: true,                       // capture native crashes
  attachStacktrace: true,

  beforeSend(event) {
    // Strip PII before sending to Sentry (third party)
    if (event.user) { delete event.user.email; delete event.user.ip_address }
    // Remove account numbers, meter IDs from breadcrumbs
    event.breadcrumbs?.values?.forEach(b => {
      if (b.data?.accountNumber) b.data.accountNumber = '[REDACTED]'
    })
    return event
  }
})

// Source maps — so Sentry shows real TypeScript line numbers not minified JS
# In CI: npx sentry-cli react-native upload-dsym

// Add context to errors — helps debug account-specific issues
Sentry.setUser({ id: user.id })  // ID only — no PII
Sentry.setTag('app_version', appVersion)
Sentry.setTag('platform', Platform.OS)

// Wrap screen with error boundary
export function UsageScreen() {
  return (
    <Sentry.ErrorBoundary fallback={<ErrorFallback />}>
      <UsageContent />
    </Sentry.ErrorBoundary>
  )
}

QHow do you track down a memory leak in a React Native app?▶
  • Confirm it's a leak: Use Flipper's Hermes Debugger memory profiler or Xcode Instruments. Take heap snapshots at T=0, T=5min, T=15min. If heap grows without stabilising, you have a leak.
  • Common culprits in React Native:
    • Event listeners added in useEffect not removed in the cleanup function
    • Interval/timeout set but never cleared (missing clearInterval in cleanup)
    • Subscriptions (Redux store, EventEmitter) not unsubscribed on component unmount
    • Large images cached without a size limit (FastImage cache, or raw require() of large local images)
    • Closures holding references to large data — e.g. a callback capturing the full usage dataset
  • Fix pattern: Every useEffect that adds something should remove it in the return cleanup. Every subscription should have a corresponding unsubscribe.
