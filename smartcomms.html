React Architecture for an Enterprise SaaS Platform

Component Structure

  • Feature-based folders — not type-based. /campaigns, /contacts, /templates
  • Co-locate: component + test + styles + query in same folder
  • Shared UI: design system in /components/ui — buttons, tables, modals
  • Domain logic out of components — custom hooks and service modules
  • Error boundaries per feature, not just at app root

State Management

  • Apollo Cache as the primary "store" for server data
  • Zustand or React Context for UI state (modals, filters, selected rows)
  • URL state for shareable views — campaign filters, pagination
  • Avoid Redux unless team already uses it — Apollo handles server state
  • Form state: React Hook Form — performant, TypeScript-first

Interview Questions

QHow do you handle optimistic updates in a GraphQL mutation — and what happens when the mutation fails?▶
Optimistic updates update the Apollo cache immediately before the server responds, so the UI feels instant.
  • Use the optimisticResponse option on useMutation — provide the expected response shape
  • Apollo writes this to the cache immediately, triggering a re-render
  • When the real response arrives, Apollo replaces the optimistic data with real data
  • On failure: Apollo automatically rolls back the optimistic update and the cache returns to its previous state. You then show an error toast/notification.
  • For Pendula: "Send message" mutation — optimistically show message as 'queued', roll back to 'failed' if the mutation errors
QHow do you decide between polling, subscriptions, and SSE for live data in a React app?▶
  • Polling (pollInterval in Apollo): Simplest. Good for low-frequency updates or where WebSocket infra isn't available. Wastes bandwidth if nothing changed.
  • GraphQL Subscriptions: Push from server. Best for high-frequency, user-facing live data — live campaign delivery stats. Requires WebSocket support in the server and infra.
  • SSE: One-way server push over HTTP. Simpler than WebSockets, no special server config. Good for notifications and status streams.
  • My approach for Pendula: Subscriptions for the live delivery dashboard (high value, users watching it); polling for background status refreshes (campaign list, every 30s); SSE for system notifications.

// Generic paginated response — used everywhere in enterprise APIs
interface PaginatedResponse<T> {
  edges: Array<{ node: T; cursor: string }>
  pageInfo: { hasNextPage: boolean; endCursor: string | null }
  totalCount: number
}

// Generic hook for paginated GraphQL queries
function usePaginatedQuery<T>(
  query: DocumentNode,
  variables: Record<string, unknown>,
  getPage: (data: unknown) => PaginatedResponse<T>
) {
  const { data, fetchMore } = useQuery(query, { variables })
  const page = data ? getPage(data) : null

  const loadMore = () => page?.pageInfo.hasNextPage
    ? fetchMore({ variables: { ...variables, after: page.pageInfo.endCursor } })
    : undefined

  return { items: page?.edges.map(e => e.node) ?? [], loadMore, totalCount: page?.totalCount ?? 0 }
}
AWS · Must Know
Amazon SQS
SQS is the backbone of Pendula's event-driven messaging pipeline. You will investigate queue depth issues, message failures, DLQ alerts, and processing lag in production. Know this deeply.
Why SQS is Central Here Pendula sends bulk messages (email, SMS) at scale. Each send is likely an SQS message processed by workers. When something breaks — the SQS queue is where you start investigating.

SQS Fundamentals — Know These Cold

ConceptWhat It IsWhy It Matters for Production
Standard QueueAt-least-once delivery, best-effort orderingMessages can be duplicated — consumers must be idempotent
FIFO QueueExactly-once, strict order within message groupHigher cost, lower throughput — use for ordered workflows
Visibility TimeoutTime a message is hidden after being received (default 30s)If consumer crashes, message reappears after timeout. Must be longer than max processing time.

Long PollingWait up to 20s for messages (vs short poll)Reduces empty responses and cost — always enable in production
Message Retention1min–14 days (default 4 days)If workers are down for days, messages expire — data loss risk
Batch SizeUp to 10 messages per receive callHigher batch = more efficient, but one failure can affect whole batch handling

Investigation Checklist Check in this order — don't jump to conclusions.
  • 1. Are consumers running? Check EKS pods — are they in CrashLoopBackOff, OOMKilled, or just stopped?
  • 2. Consumer throughput: CloudWatch metric NumberOfMessagesSent vs NumberOfMessagesDeleted — is deletion falling behind?
  • 3. Processing time: Is each message taking longer than usual? Check app logs for slow operations (DB queries, external API calls)
  • 4. Downstream blocked? Are messages piling up because SES is rate-limited or an external API is timing out?
  • 5. Consumer count: Scale up consumers (increase pod replicas) if CPU/memory headroom allows
  • 6. Visibility timeout: If messages keep reappearing, consumers aren't finishing within the timeout — extend it or investigate slowness

// Idempotency pattern — check before processing
async function processMessage(message: SQSMessage) {
  const { messageId, body } = message
  const payload = JSON.parse(body) as SendMessagePayload

  // Check if already processed using the SQS MessageId as idempotency key
  const already = await db.exists('processed_messages', { messageId })
  if (already) {
    console.log(`Duplicate message ${messageId} — skipping`)
    return  // still delete from queue — just don't reprocess
  }

  // Process atomically — insert idempotency record + do the work in one transaction
  await db.transaction(async (tx) => {
    await tx.insert('processed_messages', { messageId, processedAt: new Date() })
    await sendEmailViaSES(payload, tx)
  })
}

// Cleanup: TTL on processed_messages — keep 7 days, then purge

SQS Interview Questions

QWhat is the difference between SQS Standard and FIFO queues, and when would you use each for a messaging platform?▶
  • Standard: At-least-once delivery, best-effort ordering, nearly unlimited throughput. Messages can arrive out of order or be duplicated. Consumers must handle both.
  • FIFO: Exactly-once within a message group, strict order preserved, 3,000 msg/s (with batching). Higher cost.
  • For Pendula's bulk sends: Standard queue — throughput matters more than order. Emails to 100k contacts should fly out in parallel, not in a single ordered queue.
  • For FIFO use case: If there's a workflow where a contact must receive messages in a specific sequence (welcome → day 3 → day 7), FIFO with the contact ID as message group ID preserves that order.
QA DLQ alarm fires at 2am. Walk me through exactly what you do.▶
  • 1. Don't panic — assess severity first. How many messages in DLQ? 1 = investigate but low urgency. 1000 = active campaign sending is broken, escalate.
  • 2. Pull a sample message from DLQ via CLI or AWS Console. Read the body — which campaign, which customer, what action?
  • 3. Check app logs for that message ID / campaign ID. Find the exception or error that caused failure.
  • 4. Common causes: Malformed message body, DB connection pool exhausted, SES rate limit hit, external API timeout, code exception on a specific data shape
  • 5. If fixable now: Fix, deploy (or config change), then redrive DLQ slowly
  • 6. If not fixable now: Extend DLQ retention to buy time, leave handover note for AU team with full context, alert SLO impact
  • 7. Document: Write incident note immediately while context is fresh

// SES → SNS → SQS → Your Handler (standard pattern)
// SES publishes bounce/complaint events to SNS topic
// SNS fans out to SQS queue → your consumer processes them

interface SESNotification {
  notificationType: 'Bounce' | 'Complaint' | 'Delivery'
  bounce?: {
    bounceType: 'Permanent' | 'Transient' | 'Undetermined'
    bounceSubType: string
    bouncedRecipients: Array<{ emailAddress: string; diagnosticCode?: string }>
  }
  complaint?: {
    complainedRecipients: Array<{ emailAddress: string }>
    complaintFeedbackType?: string
  }
}

async function handleSESNotification(notification: SESNotification) {
  switch (notification.notificationType) {
    case 'Bounce': {
      const { bounceType, bouncedRecipients } = notification.bounce!
      for (const recipient of bouncedRecipients) {
        await suppressionList.add({
          email: recipient.emailAddress,
          reason: bounceType === 'Permanent' ? 'hard_bounce' : 'soft_bounce',
          permanent: bounceType === 'Permanent',
        })
        // Update contact record in Pendula
        await contacts.markUndeliverable(recipient.emailAddress, bounceType)
      }
      break
    }
    case 'Complaint': {
      for (const r of notification.complaint!.complainedRecipients) {
        await suppressionList.add({ email: r.emailAddress, reason: 'complaint', permanent: true })
        await contacts.unsubscribe(r.emailAddress) // GDPR: treat complaints as opt-out
      }
      break
    }
  }
}

QHow would you safely deploy a new version of a service in Kubernetes with zero downtime?▶
  • Rolling update (default Kubernetes strategy): new pods come up, old pods come down gradually. Zero downtime as long as readiness probes are correct.
  • Readiness probe is critical: Kubernetes only routes traffic to a pod after its readiness probe passes. If your new pod takes 30s to warm up, set initialDelaySeconds: 30.
  • PodDisruptionBudget: Ensures minimum number of pods stay available during rolling update. Set minAvailable: 1 at minimum.
  • Canary deployments: Deploy new version to 10% of pods first. Monitor error rates. If healthy, proceed to 100%.
  • Feature flags: Ship code dark, enable for 1% of traffic via flag, ramp up. Decouples deploy from release.
  • For consumer workers: Let existing pods drain in-flight SQS messages before terminating — use terminationGracePeriodSeconds long enough for max processing time.
Systems
Distributed & Event-Driven Systems
Pendula's platform is fundamentally event-driven. Messages flow through queues, trigger workers, update state asynchronously. Know the patterns, failure modes, and trade-offs.

Core Patterns

Event-Driven Architecture

  • Services communicate via events, not direct calls
  • Producer publishes event (e.g. campaign.send_requested)
  • Consumers subscribe and react independently
  • Decoupled: producer doesn't know or care who consumes
  • Trade-off: harder to trace end-to-end, eventual consistency

Message Queue Pattern (Pendula)

  • Campaign created → event onto SQS queue
  • Worker pool picks up messages, sends via SES
  • Delivery events (bounce/complaint) flow back via SNS→SQS
  • All state updated asynchronously — eventual consistency
  • Retry via SQS visibility timeout + DLQ for permanent failures

Failure Modes in Distributed Systems

FailureSymptomMitigation
Partial failureSome messages sent, some not — inconsistent stateIdempotent consumers, transactional outbox pattern
Message orderingEvents arrive out of orderInclude sequence/version in message, handle out-of-order in consumer
Consumer lagQueue depth growing — processing can't keep upScale consumers, batch processing, reduce processing time
Poison pillOne malformed message blocks the queueDLQ with maxReceiveCount; validate messages on receipt
Cascading failureOne slow service blocks all upstreamCircuit breaker, bulkhead pattern, timeouts on all calls
Split brainTwo instances think they own the same workLeader election, distributed locks (Redis), idempotency

Transactional Outbox Pattern

Solving the Dual-Write Problem Never write to DB and publish to SQS as two separate operations — one can fail. Use the outbox: write both in one DB transaction, a relay picks up and publishes to SQS. 
// Without outbox — DANGEROUS: DB write succeeds, SQS publish fails
await db.updateCampaignStatus('sending')  // succeeds
await sqs.send(message)                  // fails — campaign is "sending" but nothing queued!

// With outbox — SAFE: both happen in one transaction
await db.transaction(async (tx) => {
  await tx.updateCampaignStatus('sending')
  await tx.insertOutboxMessage({        // writes to outbox table in same TX
    eventType: 'campaign.send_requested',
    payload: { campaignId, recipientCount },
    status: 'pending',
  })
})
// Relay process polls outbox table, publishes to SQS, marks as published
// If relay fails, it retries — outbox records are persistent
QWhat is eventual consistency and how do you handle it in a frontend that needs to show live status?▶
Eventual consistency means the system will become consistent, but not instantly. After an action (send campaign), the state might not reflect in the UI immediately because async workers haven't processed it yet.
  • Optimistic UI: Update the UI immediately assuming success. If the server later disagrees, reconcile.
  • Polling or subscriptions: Keep refetching state until it reflects the expected change — with a timeout and user feedback if it takes too long
  • Status model: Model intermediate states explicitly — don't just show "sending" and "sent". Show "queued", "in progress (X/Y)", "delivered", "completed with errors"
  • User communication: "Your campaign has been queued and will send within the next few minutes" sets expectation. Don't imply instant delivery.

What happens to SQS messages when visibility timeout expires before processing completes?
The message becomes visible again in the queue and another consumer can pick it up — resulting in duplicate processing. This is why consumers must be idempotent. Fix: set visibility timeout longer than your maximum processing time, or extend it programmatically (ChangeMessageVisibility) if processing is taking longer than expected.

What is IRSA and why does it matter for EKS pods that call SQS?
IAM Roles for Service Accounts — lets pods assume an IAM role without hardcoded credentials. A Kubernetes service account is annotated with a role ARN. When the pod uses that service account, it gets temporary AWS credentials via OIDC. If your pod can't call SQS, check: (1) the service account has the right role ARN annotation, (2) the IAM role has an SQS policy, (3) the OIDC provider is configured for the cluster.

What is the difference between a hard bounce and a soft bounce in SES?
Hard bounce: Permanent failure — email address doesn't exist, domain invalid, address blocked. Must suppress immediately and permanently. Soft bounce: Temporary failure — mailbox full, server temporarily unavailable. Can retry with exponential backoff. Suppress after 3+ soft bounces. Hard bounces damage reputation faster — treat them as an emergency signal about your contact list quality.

How does KEDA scale SQS consumers on Kubernetes?
KEDA (Kubernetes Event-Driven Autoscaling) queries SQS ApproximateNumberOfMessagesVisible on a configurable interval. It calculates desired replicas as: ceil(queueLength / targetQueueLength). When the queue depth exceeds the threshold per pod, it increases replicas up to maxReplicaCount. When the queue drains, it scales down to minReplicaCount. This means zero manual scaling — the queue drives the workers automatically.

Frontend & Systems

What is the Apollo fetchPolicy: 'cache-and-network' and when do you use it?
Returns cached data immediately (fast UI), then fires a network request and updates the UI when the response arrives. Useful for: dashboards that should feel instant but must stay fresh. Compare to: 'cache-first' (only fetch if nothing in cache — stale risk), 'network-only' (always fetch — slower but always fresh). For Pendula's campaign list, cache-and-network is ideal — show last known state instantly, then update.

What is the transactional outbox pattern and why does it matter?
Solves the dual-write problem: you need to update your DB AND publish to SQS atomically, but these are two different systems. Solution: write the event to an outbox table in the same DB transaction as your state update. A relay process then reads the outbox and publishes to SQS, marking records as published. If the relay fails, it retries — records are persistent. This guarantees the DB state and the event queue are always consistent.

What CloudWatch Insights query do you write to find the root cause of a spike in errors?
fields @timestamp, errorCode, @message | filter level = "ERROR" | stats count(*) as n by errorCode | sort n desc — groups errors by type, most frequent first. Then drill into the top error type: fields @timestamp, @message, campaignId, userId | filter errorCode = "DB_TIMEOUT" | sort @timestamp asc | limit 50 — gives you the sequence of events around that error type.

What is the difference between a liveness probe and a readiness probe in Kubernetes?
Liveness probe: Is the container alive? If it fails, Kubernetes restarts the pod. Use for detecting deadlocks or hung processes that are running but not functional. Readiness probe: Is the container ready to receive traffic? If it fails, the pod is removed from the Service's endpoints but NOT restarted. Use during startup or when temporarily overloaded. A pod can be alive (liveness passing) but not ready (readiness failing) — it keeps running but receives no traffic.
